# OpenEidon — план работ

Дата: 2026-08-21. Статус: черновик-план, фазы идут по порядку, но 4–6 можно вести параллельно после завершения 0–2.

Принятые решения:
- **UI**: основной интерфейс — `frontend/src/pages/JarvisApp.tsx` («EIDON · FOX», тёмная оранжевая тема со скриншота). Desktop-обёртка — Tauri (`desktop/`), которая уже рендерит этот же frontend. `desktop-mini/` (Electron) удаляется.
- **Ребрендинг**: полный — пакет `openeidon`, CLI `eidon`, конфиг `~/.openeidon`. Атрибуция OpenJarvis сохраняется в NOTICE/README.
- **Машина**: окружение разворачивается заново на новой машине; старые деплой-заметки (`DEPLOY_STATUS.md` и т.п.) не актуальны и удаляются.

## Фаза 0 — Санитария репозитория (полдня)

Цель: репозиторий перестаёт быть «обёрткой вокруг папки» и весит адекватно.

### 0.1 Убрать node_modules из git
- `git rm -r --cached OpenJarvis-main/desktop-mini/node_modules` (уйдёт вместе с desktop-mini, см. 2.1, но из индекса убрать сразу).
- В `.gitignore`: универсальное правило `node_modules/` вместо точечных путей.

### 0.2 Поднять код в корень
- Содержимое `OpenJarvis-main/` → корень репозитория (`git mv`).
- Разрешить конфликты дублей: LICENSE, NOTICE, README (корневой README — основной), AGENT.md.
- После переезда GitHub Actions начнут работать (сейчас workflows лежат в `OpenJarvis-main/.github/` и не запускаются вообще).

### 0.3 Удалить мусор
- `.run-logs/` (COMMAND_LOG.md, ru-smoke.wav)
- `DEPLOY_PLAN.md`, `DEPLOY_STATUS.md` (содержит личный путь `C:\Users\olivi\...`)
- `REVIEW.md` (инструкции ревью PR апстрима), `memory.md` (перенести полезное в docs, см. 6.2)
- `desktop-mini/18apr.md` (рабочий дневник)
- `tsconfig.tsbuildinfo`, `.github/clone-stats/`

- `youtube_homepage.png` (байт-в-байт дубль `screenshot.png`); сам `screenshot.png` заменить на реальный скрин FOX-интерфейса
- Пустые `AGENT.md`/`CLAUDE.md` (корневые, 0 байт) — удалить; новый CLAUDE.md написать в фазе 3.

### 0.4 Решение: переписать историю
История содержит 77 МБ node_modules и личные данные. Репозиторий молодой (10 коммитов), внешних форков нет → **рекомендуется** `git filter-repo` (или свежий orphan-коммит) + force-push. После этого клон будет ~50 МБ и без утечек.

### 0.5 Починить README
- Quick Start: клонировать **свою** репу (`Yelt-sk/OpenEidon`), а не апстрим.
- Убрать битый символ `�` (строка ~16).
- Структура проекта в README должна совпадать с реальной (после 0.2 совпадёт).
- Команды обновить после ребрендинга (фаза 1): `uv run eidon ...`.

**Критерий готовности фазы**: свежий клон < 60 МБ, `src/` и `frontend/` в корне, CI триггерится на push, в репе нет личных данных.

## Фаза 1 — Ребрендинг openjarvis → openeidon (1–2 дня)

Механическая, но одноразовая работа. Делать одним большим PR, по шагам, с прогоном тестов после каждого.

### 1.1 Python-пакет
- `src/openjarvis/` → `src/openeidon/`; глобальная замена импортов (`grep -rl 'openjarvis' | xargs sed`).
- `pyproject.toml`: `name = "openeidon"`, entry point `eidon = openeidon.cli:main` (временный алиас `jarvis` можно оставить на один релиз).
- Классы/имена типа `JarvisConfig` → `EidonConfig` — вторым проходом, после зелёных тестов.

### 1.2 Пользовательские пути и конфиг
- `~/.openjarvis/` → `~/.openeidon/` + **миграция при старте**: если старая папка есть, а новой нет — переносить (или читать со старым путём как fallback).
- Env-переменные `OPENJARVIS_*` → `EIDON_*` (со старыми как deprecated fallback).

### 1.3 Rust
- Крейты `rust/crates/openjarvis-*` → `openeidon-*`, модуль PyO3, команда maturin в README/CI.

### 1.4 Frontend / desktop
- `package.json` имена, тайтлы, Tauri `productName`, идентификатор бандла, иконки (логотип уже есть в `assets/`).
- Довести до конца начатый ребрендинг в `frontend/` (сейчас смесь Eidon/Jarvis, `JarvisApp.tsx` → `EidonApp.tsx`).

### 1.5 Документация и CI
- mkdocs.yml, docs/ — глобальная замена + вычитка стартовых страниц.
- Workflows: убрать/переписать `pypi-publish.yml` (публиковать под именем `openeidon` и только когда решим), `track-clones.yml`, `take-assign.yml`, `claude-*.yml` — оценить нужность для соло-проекта.

**Критерий готовности**: `uv run eidon doctor` работает, `pytest` зелёный, `grep -ri jarvis src/` возвращает только NOTICE-упоминания об атрибуции.

## Фаза 4 — Производительность

Правило: сначала профиль, потом оптимизация. Бейзлайны — из фазы 3.

### 4.1 Backend
- **Холодный старт CLI/сервера**: `python -X importtime -m openeidon.cli` → ленивые импорты тяжёлых зависимостей (datasets, openai, telegram) — грузить по требованию, не на верхнем уровне. Часто даёт секунды.
- **config.py (1930 строк)** — проверить, не парсится ли конфиг многократно; кэшировать.
- **Горячий путь чата**: `server/routes.py` → engine: убедиться, что стриминг сквозной (никаких буферизаций полного ответа), нет блокирующих вызовов в async-обработчиках (файловый I/O, subprocess — в executor).
- **SQLite**: WAL-режим, индексы на sessions/memory, `PRAGMA synchronous=NORMAL`.
- **Rust-расширение**: инвентаризация — что реально вызывается из Python; горячие текстовые операции (чанкинг, поиск по памяти) — кандидаты на перенос в Rust.

### 4.2 Inference (новая машина)
- Прогнать `eidon init` заново — hardware-aware подбор моделей под новое железо; обновить дефолтную/fallback модели.
- Проверить и настроить: контекст-кэш Ollama, keep_alive, параллельные слоты; для мелких задач (intent classify, title generation) — отдельная маленькая быстрая модель, не основная.

### 4.3 Frontend
- `vite build` + анализ бандла (rollup-plugin-visualizer): katex и тяжёлые либы — в lazy chunks.
- Виртуализация списка сообщений при длинных чатах; мемоизация MessageBubble.
- После чистки мёртвых страниц (2.2) бандл уменьшится сам.

**Критерий готовности**: задокументированные до/после цифры по каждому пункту.

## Фаза 5 — Интеграция OpenCode

Цель: режим **AGENT** в композере FOX-UI делегирует кодинг-задачи OpenCode, а Eidon остаётся оркестратором.

### 5.1 Спайк (1 день)
- Поставить opencode на машину, проверить два канала:
  a) `opencode run "..."` — one-shot subprocess с JSON-выводом;
  b) `opencode serve` — постоянный HTTP-сервер с session API (предпочтительно: сессии, стриминг событий).
- Зафиксировать выбор канала в `docs/architecture/opencode.md`.

### 5.2 Бэкенд-мост
- Новый модуль `src/openeidon/connectors/opencode.py` (или `operators/`): менеджер процесса `opencode serve` (старт/стоп/health), клиент его API, маппинг сессий Eidon ↔ сессии opencode.
- Регистрация как tool/agent через существующий registry-паттерн (`ToolRegistry`/`AgentRegistry`) — как и все компоненты.
- Стриминг событий opencode (шаги, диффы, вывод команд) в EventBus → в существующий WS-мост (`server/ws_bridge.py`) → Trail-панель UI.
- Безопасность: whitelist рабочих директорий (у Eidon уже есть file-roots механика), явное подтверждение на запись/выполнение команд — permission-запросы прокидывать в UI.
- Конфиг: секция `[opencode]` в config.toml — путь к бинарю, порт, модель, разрешённые каталоги.

### 5.3 UI
- Режим AGENT в композере: выбор проекта (каталога), отправка задачи в opencode-сессию.
- Trail → Tools: живой лог шагов агента (файлы, команды, диффы), кнопки approve/deny.
- Карточка «OpenCode» в списке CONNECTED со статусом.

### 5.4 Синергия через MCP
- У Eidon есть свой MCP-клиент/сервер (`src/openeidon/mcp/`), opencode тоже говорит на MCP → отдать opencode доступ к инструментам Eidon (память, коннекторы, браузер) через MCP-сервер Eidon. Это глубокая интеграция «вторым этапом», после рабочего 5.2–5.3.

**Критерий готовности**: из чата Eidon задача «поправь баг в проекте X» доходит до opencode, прогресс виден в Trail, результат (дифф/отчёт) возвращается в чат.
